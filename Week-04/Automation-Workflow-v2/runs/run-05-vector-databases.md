Vector Databases & Retrieval Systems — Comprehensive Study Notes
Executive Summary

Vector databases are specialized databases built to store and search embeddings—high-dimensional numerical representations of unstructured data such as text, images, and audio. Unlike traditional relational databases, which rely on exact matches and SQL queries, vector databases perform similarity search to retrieve semantically related information.

They are a core component of Retrieval-Augmented Generation (RAG) systems, where relevant external knowledge is retrieved at runtime and supplied to a language model to generate grounded responses. Modern vector databases also incorporate advanced techniques such as HNSW indexing, payload-indexed filtering, hybrid search, quantization, and vector caching to balance retrieval quality, scalability, latency, and storage efficiency.

Selecting the right infrastructure depends on factors such as vector count, deployment constraints, workload patterns, latency requirements, and data residency rather than assuming a dedicated vector database is always necessary.

1. Key Concepts
Vector Databases vs. Relational Databases

Traditional relational databases are designed for structured data stored in rows and columns. Queries are performed using SQL and rely on exact matches.

Vector databases are optimized for unstructured data represented as embeddings. Instead of exact matching, they perform similarity searches to find items with the closest semantic meaning.

Relational Database	Vector Database
Stores structured records	Stores embeddings (vectors)
Exact-match queries	Similarity search
SQL-based retrieval	Nearest-neighbor retrieval
Best for transactional data	Best for semantic retrieval
Embeddings

Embeddings are numerical vectors generated by embedding models.

They encode the semantic or perceptual meaning of:

Text
Images
Audio

Items with similar meanings are represented by nearby vectors in high-dimensional space, enabling semantic search rather than keyword matching.

Retrieval-Augmented Generation (RAG)

RAG combines external knowledge retrieval with language models.

Instead of relying solely on information learned during training, a system retrieves relevant documents at runtime and provides them to the language model before generating a response.

Tunable Consistency

Some vector databases allow applications to choose between different consistency levels.

Preference	Benefit
Eventual consistency	Higher throughput and better performance
Strong consistency	More predictable results with lower latency trade-offs

The appropriate choice depends on the application's requirements.

"Log as Data" Architecture

Systems such as Milvus (Manu) treat the Write-Ahead Log (WAL) as the foundation of the database.

Instead of tightly coupling read and write operations:

Writes are recorded in the WAL.
Read components consume data independently.
Read and write systems can scale separately.

This architecture enables better scalability and flexibility.

2. Important Techniques
HNSW (Hierarchical Navigable Small World)

HNSW is one of the most widely used indexing algorithms for Approximate Nearest Neighbor (ANN) search.

It builds multiple layers of proximity graphs that allow efficient navigation through vectors.

Advantages

Fast nearest-neighbor search
Logarithmic search complexity
Excellent scalability for large datasets
Payload-Indexed Filtering

Many searches require metadata filtering (for example, searching only documents from a particular user or category).

Instead of:

Search → Retrieve Results → Apply Metadata Filter

Payload-indexed filtering performs:

Search + Metadata Filtering Together

This prevents the severe recall degradation that often occurs with post-filtering.

Hybrid Search

Hybrid search combines multiple retrieval techniques.

It uses:

Dense vector similarity
Sparse keyword search (BM25 or TF-IDF)
Re-ranking

This allows systems to capture:

Semantic similarity
Exact keyword matches

resulting in higher-quality retrieval.

Quantization

Quantization compresses vector representations to reduce storage requirements.

The research mentions:

Scalar Quantization (SQ)
Product Quantization (PQ)

Benefits include:

Reduced memory usage
Lower storage costs
Minimal reduction in retrieval accuracy
Vector Caching

Generating embeddings repeatedly can increase latency and API costs.

Using tools such as CacheBackedEmbeddings allows previously computed embeddings to be stored locally.

Benefits:

Lower latency
Reduced API costs
Less repeated computation

4. Practical Applications
E-commerce Recommendations

Products and users are represented as embeddings.

Recommendation systems compare user vectors with product vectors to identify semantically similar products in real time.

Video Deduplication

Important video frames are converted into embeddings.

Similarity search identifies duplicate or near-duplicate videos across massive archives, reducing storage and management costs.

Cybersecurity

Virus signatures are represented as vectors.

Similarity search helps identify suspicious software by comparing unknown samples with known malware signatures.

Edge Deployment

Applications such as hospital sepsis diagnostic systems operate entirely on on-premises infrastructure.

Keeping inference local ensures sensitive patient data remains within secure organizational boundaries.

Self-Hosting Migration

Some startups migrate from:

Pinecone → Self-hosted Qdrant (Docker Compose)

Reason:

As monthly query volumes grow, self-hosting can become significantly more cost-effective than managed services.

6. Common Beginner Misunderstandings
Believing ANN Benchmarks Reflect Production Performance

Synthetic ANN benchmarks often exclude:

Metadata filtering
Concurrent write pressure

Real-world systems may experience dramatically higher latency under these conditions.

Assuming Managed Services Always Cost Less

Managed platforms provide an easy starting point.

However, research suggests a tipping point around 80–100 million queries per month, after which self-hosting on dedicated hardware may become significantly cheaper.

Thinking Embeddings Are Anonymous

Embeddings are not inherently anonymous.

Research highlights Vector Inversion Attacks, which may partially reconstruct original text or sensitive information from stolen vectors.

Assuming Dedicated Vector Databases Are Always Required

Many beginners immediately choose a dedicated vector database.

The research notes that pgvector on PostgreSQL is often sufficient for datasets under 10 million vectors, depending on workload characteristics.

7. Disagreements Between Sources
PostgreSQL Scalability

The sources disagree about PostgreSQL's practical limits.

One source suggests PostgreSQL can support production workloads up to 50 million vectors.

Another suggests dedicated vector databases become preferable somewhere between 1–5 million vectors due to performance limitations.

The Future of RAG

One viewpoint argues that Pinecone's Nexus architecture represents the end of the traditional RAG era.

Another argues this conclusion is premature because Nexus still fundamentally manages and retrieves vectors.

Query Language Standardization

Some analysts question whether Pinecone's KnowQL could increase vendor lock-in because it lacks SQL-style cross-vendor standardization.

Benchmark Reliability

Some sources argue commonly reported benchmarks do not accurately reflect production environments because they omit realistic operational conditions.

8. Interview Questions
1. What is the difference between a vector database and a relational database?

A vector database stores embeddings and retrieves semantically similar items through similarity search, whereas a relational database stores structured records and retrieves data through exact-match SQL queries.

2. What is an embedding?

A numerical vector that represents the semantic or perceptual meaning of text, images, or audio.

3. How does Retrieval-Augmented Generation (RAG) work?

RAG retrieves relevant external knowledge from a vector database at runtime and supplies it to a language model to generate grounded responses.

4. Why is HNSW widely used?

Because its layered graph structure enables efficient approximate nearest-neighbor search with logarithmic complexity.

5. What problem does payload-indexed filtering solve?

It integrates metadata filtering directly into graph traversal, avoiding the severe recall degradation associated with post-filtering.

6. What is hybrid search?

A retrieval approach that combines dense vector similarity, sparse keyword search (BM25 or TF-IDF), and re-ranking.

7. Why is quantization important?

It compresses vectors, reducing storage and memory usage while maintaining most retrieval accuracy.

8. Why cache embeddings?

Caching avoids recomputing embeddings, reducing latency and API costs.

9. Why shouldn't infrastructure decisions rely only on ANN benchmarks?

Because benchmark results often exclude metadata filtering and concurrent write pressure, making them less representative of production performance.

10. What factors should guide vector database selection?

Infrastructure should be selected by evaluating vector count, workload characteristics, deployment constraints, latency requirements, and data residency needs.

Key Takeaways
Vector databases enable semantic retrieval through similarity search rather than exact matching.
Embeddings are the foundation of modern semantic search and RAG systems.
HNSW, payload-indexed filtering, hybrid search, quantization, and vector caching are key techniques for building scalable retrieval systems.
Infrastructure choices should be driven by workload characteristics, deployment constraints, latency, and vector count—not by assumptions.
Synthetic benchmarks, managed service costs, and embedding privacy all have important real-world limitations that beginners often overlook.
Current research contains differing opinions on PostgreSQL scalability, the future of RAG, and query language standardization, highlighting that infrastructure decisions should be context-dependent rather than one-size-fits-all.
